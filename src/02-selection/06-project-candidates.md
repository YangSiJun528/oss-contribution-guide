# 6장. 프로젝트 후보군의 구성

첫 프로젝트는 유명세보다 계속 살펴볼 개인적 이유를 기준으로 고릅니다. 처음부터 하나를 확정하지 말고 여러 후보를 만들어야 기여 조건이 맞지 않거나 적합한 작업이 없을 때 다른 후보로 이동할 수 있습니다.

## 지속 가능성 기준

변경을 끝까지 이해하고 설명하려면 작업 중에 만나는 문서와 코드, 실패와 리뷰를 계속 살펴볼 이유가 있어야 합니다. 다음과 같은 관계가 그 이유가 될 수 있습니다.

1. 현재 사용하고 있는 프로젝트
2. 관심 있거나 공부하고 싶은 분야의 프로젝트
3. 사용해 보고 싶었던 도구나 라이브러리
4. 이전 프로젝트·포트폴리오·지원 분야와 관련된 프로젝트

특정 관계가 다른 관계보다 항상 우선하는 것은 아닙니다. 후보를 찾는 시작점으로 사용하고, 실제 기여 가능성은 다음 장에서 별도로 검증합니다.

## 후보 탐색 경로

평소 사용하는 애플리케이션의 의존성, 사이드 프로젝트에서 사용한 라이브러리, 관심 분야의 재단·기업·개발자 계정에서 후보를 찾을 수 있습니다. GitHub의 탐색·검색 기능과 관심 주제를 사용해 후보를 넓힐 수도 있습니다.

하지만 검색 결과에 나오는 것과 기여하기에 적합한 것은 다릅니다. 이 단계에서는 검증하지 말고, 살펴볼 이유와 함께 후보로만 기록합니다.

## 후보군의 다변화

이 모임에서는 약 5개의 후보를 먼저 고르기를 권합니다. 하나의 생태계에서도 핵심 프로젝트, 구체적인 라이브러리, 개발 도구는 외부 기여 여건이 다를 수 있습니다. 다른 규모와 운영 형태의 후보를 함께 두면 특정 유형에 지나치게 의존하는 것을 피할 수 있습니다.

후보 수를 정확히 5개로 맞추는 것이 목표는 아닙니다. 다음 단계에서 조건이 맞지 않은 후보를 제외해도 탐색을 다시 시작하지 않을 정도의 선택지를 만드는 것이 목표입니다.

## 후보 부재의 판단

여러 경로를 살펴봐도 지속해서 살펴볼 이유가 있는 프로젝트를 찾지 못했다면 기여를 억지로 진행하지 않는 편이 낫습니다. 임의로 고른 프로젝트에서는 작업의 의미를 이해하고 리뷰까지 동기를 유지하기 어렵습니다.

관심 분야를 더 살펴보거나, 직접 사용해 보거나, 나중에 다시 시도해도 됩니다. 후보가 없다는 것은 실패가 아니라 현재 조건에서의 유보 판단입니다.

## 후보군 기록

후보를 다음과 같이 정리합니다.

| 항목 | 기록 내용 |
| --- | --- |
| 프로젝트 | 이름과 공식 저장소 |
| 선정 이유 | 사용, 학습, 관심, 이전 경험과의 관계 |
| 현재 지식 | 사용 경험과 알고 있는 범위 |
| 확인 필요 | 기여 절차, 운영 상태, 작업 후보 등 |

> **모임 체크포인트**

> 프로젝트 후보군과 각 후보를 선정한 이유를 모임 채널에 공유합니다. 이 단계에서 하나를 확정하지 않습니다.
