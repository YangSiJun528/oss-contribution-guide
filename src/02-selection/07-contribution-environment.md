# 7장. 기여 환경의 검증

프로젝트의 실제 기여 가능성은 Star, Commit 수, 문서 하나로 판단할 수 없습니다. 공식 문서에서 제시한 조건과 최근 Issue·PR에서 보이는 실제 운영을 함께 확인해야 합니다. 이 가이드보다 해당 프로젝트의 안내가 우선합니다.

## 문서상 기여 조건

먼저 프로젝트가 제공하는 공식 정보를 읽습니다. 파일 이름과 위치는 프로젝트마다 다르고, 저장소가 아닌 별도 웹사이트와 조직 공통 저장소에 있을 수도 있습니다.

| 대표 위치 | 확인할 정보 |
| --- | --- |
| `README.md`, `docs/`, 공식 웹사이트 | 프로젝트의 목적, 사용법, 상태와 다른 문서의 위치 |
| `LICENSE`, `COPYING`, `NOTICE`, `COPYRIGHT` | 사용·수정·배포 조건과 고지 |
| `CONTRIBUTING.md` | 개발 환경, 테스트, Commit, Issue·PR 제출 방법 |
| `DEVELOPMENT.md`, `HACKING.md` | 빌드, 실행, 디버깅 등 개발 방법 |
| `CODE_OF_CONDUCT.md` | 기대하는 행동, 금지 행동과 신고 방법 |
| `SECURITY.md` | 보안 취약점을 비공개로 신고하는 방법 |
| `GOVERNANCE.md`, `MAINTAINERS`, `OWNERS`, `CODEOWNERS` | 의사결정 구조, 담당자, 검토·승인 권한 |
| `SUPPORT.md` | 사용 질문과 지원 요청 경로 |
| `CHANGELOG.md`, 릴리스 노트, `ROADMAP.md` | 최근 변경과 향후 방향 |
| CLA, DCO, sign-off 안내 | 기여자가 동의하거나 확인할 권리 조건 |
| `AI_POLICY.md`, `LLM_POLICY.md`, 개발자 가이드 | AI 사용 범위와 공개 방법 |

이 표는 확인 대상의 지도이지 필수 파일 목록이 아닙니다. 규모가 작은 프로젝트에는 `GOVERNANCE`나 `ROADMAP`이 없을 수 있습니다.

## 권리·약정·AI 조건

[2장. OSS의 권리 구조](../01-foundations/02-rights.md)에서 살펴본 라이선스, CLA, DCO를 실제 후보에 대해 확인합니다. 재직자라면 회사 정책이 해당 프로젝트와 작업에 적용되는지도 확인합니다.

AI를 사용할 계획이라면 정책을 작업 후가 아닌 이 단계에서 확인합니다. AI 생성물 제출을 금지하는 프로젝트를 선택한 뒤 작업을 끝낸 후 알게 되면 작업 전체를 사용할 수 없게 될 수 있습니다.

## 실제 운영 조건

문서가 있어도 오래되었거나 실제 운영과 다를 수 있습니다. 최근 Issue와 PR에서 다음을 확인합니다.

- 새로운 외부 기여자의 PR도 최근에 검토되고 병합되는가?
- 유지보수자가 유효한 Issue와 PR에 응답하는가?
- 거절과 중단의 이유를 확인할 수 있는가?
- 문서에 없는 Issue 선행, 테스트, Commit 관행이 있는가?
- 진행 중인 PR과 같은 작업을 하려는 사람이 지나치게 많은가?
- 필요한 유지보수가 장기간 중단된 징후가 있는가?

하나의 느린 응답이나 거절만으로 프로젝트를 판단하지 않습니다. 대표적인 작업 여러 개의 흐름과 최근 몇 달의 운영을 함께 보고 반복되는 패턴을 찾습니다.

## 표면적 지표의 한계

GitHub Star 수는 생태계의 규모와 대중의 관심을 보여줄 수 있지만 리뷰 여력과 외부 기여 수용 여부를 보장하지 않습니다. 유명한 언어·프레임워크의 핵심 저장소는 작업 경쟁과 검토 기준이 높을 수 있으므로 같은 생태계의 구체적인 라이브러리와 도구도 함께 보는 편이 낫습니다.

Commit 개수와 간격에도 절대적인 기준은 없습니다. 안정된 프로젝트는 변경이 적을 수 있습니다. 횟수보다 필요한 Issue와 PR에 꾸준히 응답하는지를 봅니다.

## 후보 확정 조건

문서와 실제 운영을 검토한 뒤 후보별로 다음을 정리합니다.

| 판단 축 | 기록 내용 |
| --- | --- |
| 공식 조건 | 기여 절차, 권리 약정, AI 정책, 필수 검증 |
| 실제 운영 | 외부 기여 수용, 응답, 결정 경로, 문서와의 차이 |
| 진입 여건 | 설치·실행 가능성, 필요 배경지식, 작업 경쟁도 |
| 불확실성 | 확인하지 못한 조건과 추가로 물어야 할 내용 |

우선순위가 높은 1~2개의 프로젝트를 직접 설치하고 사용해 봅니다. 이 과정에서 사용법을 이해하기 어렵거나 개발 환경을 구성할 수 없다면 우선순위를 다시 조정합니다.

> **모임 체크포인트**
>
> 우선 후보 1~2개와 최근 운영을 확인한 근거, 확인하지 못한 조건을 공유합니다.
