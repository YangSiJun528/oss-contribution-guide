# 11장. 제출 전 검증

제출 전 검증의 완료 상태는 단순히 “테스트가 통과했다”가 아닙니다. 자동화 검사, 전체 diff, 공개하면 안 되는 정보, 제출자의 설명 가능성까지 확인해야 합니다.

## 자동화 검증

프로젝트가 `CONTRIBUTING`과 개발 문서에서 요구한 명령을 사용합니다. 일반적으로 확인할 대상은 다음과 같지만 정확한 범위는 프로젝트가 정합니다.

- 문제를 재현하고 방지하는 테스트
- 관련 모듈과 프로젝트 전체의 테스트
- 빌드와 타입 검사
- 포맷터와 린터
- 생성 코드·문서·스냅샷 갱신

명령이 실패하면 변경 전부터 있던 실패인지, 자신의 변경으로 생긴 실패인지 구분합니다. 확인하지 못한 실패를 무시하거나 통과했다고 기록하지 않습니다.

## 전체 diff 검토

Commit과 PR에 포함될 전체 diff를 첫 줄부터 끝까지 직접 읽습니다. 각 변경에 대해 다음을 묻습니다.

- 이 변경은 [10장의 범위](10-scope-control.md)에 포함되는가?
- 동작을 바꾼 이유를 설명할 수 있는가?
- 예상하지 못한 호환성·성능·보안 영향이 있는가?
- 임시 디버깅 코드와 주석이 남았는가?
- 포맷팅, 줄바꿈, 생성 파일이 불필요하게 바뀌었는가?
- lockfile과 의존성 변경이 의도한 것인가?

다른 도구가 diff를 요약했더라도 요약만 보고 제출하지 않습니다. 실제로 공개되는 내용은 diff 전체이기 때문입니다.

## 무관한 변경과 임시 파일

문제 해결과 관련없는 리팩터링, 오탈자, 설정 변경을 제거하거나 별도 작업으로 분리합니다. 로컬 개발에만 필요한 파일, IDE 설정, 빌드 결과물, 로그, 임시 스크립트도 제출 대상에서 제외합니다.

필요한 생성 파일과 lockfile은 무조건 제거하지 않고 프로젝트 관행을 따릅니다. 핵심은 해당 변경이 필요한 이유를 설명할 수 있는지입니다.

## 공개 정보 검증

Commit 기록과 PR은 공개 기록으로 남을 수 있습니다. 다음 정보가 포함되지 않았는지 확인합니다.

- API 키, 토큰, 암호, 인증서와 비밀키
- 이메일, 전화번호, 실명과 필요하지 않은 계정 정보
- 사내 시스템, 비공개 URL과 제3자의 정보
- 개인 디렉터리와 사용자 이름이 포함된 로컬 경로
- Commit 이메일과 저자 정보

비밀정보를 이미 Commit했다면 파일에서 지우는 것만으로 해결되지 않을 수 있습니다. 해당 키를 폐기·교체하고, 프로젝트의 보안 절차를 따릅니다.

## 검증 결과의 표현

제출할 때는 실제로 실행한 명령과 결과를 기록합니다. 확인하지 못한 환경과 테스트는 그 사실을 그대로 적습니다.

```text
실행한 검증:
- 명령·절차: 결과

확인하지 못한 내용:
- 대상: 확인하지 못한 이유
```

## 제출자 설명 가능성

최종적으로 다음 질문에 도구의 요약을 읽지 않고도 답할 수 있어야 합니다.

- 무슨 문제를 해결하는가?
- 왜 이 방법을 사용했는가?
- 각 변경은 어떤 동작에 영향을 주는가?
- 문제가 해결되었다는 것을 어떻게 확인했는가?
- 남은 한계와 확인하지 못한 내용은 무엇인가?

AI가 변경을 만들었더라도 이 기준은 달라지지 않습니다. 설명할 수 없는 변경은 제출하지 않습니다.

## 제출 전 점검표

- [ ] 성공 기준을 검증하는 테스트를 실행했다.
- [ ] 프로젝트가 요구한 빌드·포맷·린트·테스트를 실행했다.
- [ ] 전체 diff를 첫 줄부터 끝까지 읽었다.
- [ ] 무관한 변경과 임시 파일을 제거했다.
- [ ] 비밀정보, 개인정보와 로컬 경로를 확인했다.
- [ ] 실행한 검증과 미확인 내용을 구분했다.
- [ ] 모든 변경의 이유와 동작을 설명할 수 있다.
