# 10장. 변경 범위의 통제

검토 가능한 변경은 하나의 문제를 해결하는 데 필요한 내용만 포함합니다. 좋아 보이는 리팩터링과 포맷팅을 함께 넣으면 변경 이유와 영향을 구분하기 어려워집니다.

## 최소 해결안

[9장의 성공 기준](09-problem-and-done.md#성공-기준)을 만족시키는 가장 작은 변경을 먼저 설계합니다. 최소라는 말은 코드 줄 수를 억지로 줄이라는 뜻이 아닙니다. 변경의 이유를 하나로 설명할 수 있고, 각 부분이 그 이유를 위해 필요해야 한다는 뜻입니다.

구현 전에 예상하는 변경을 짧게 적습니다.

- 변경할 동작과 모듈
- 추가·수정할 테스트
- 유지해야 할 기존 동작
- 의도적으로 포함하지 않을 변경

## 관련 없는 변경의 분리

작업 중 발견한 다른 버그, 오탈자, 리팩터링 기회는 현재 변경에 자동으로 포함하지 않습니다. 현재 문제의 성공 기준과 관계없다면 별도 Issue나 PR로 분리합니다.

파일 전체에 포맷터를 적용하거나 자동 생성 결과를 갱신해 수많은 줄이 바뀌다면, 실제 동작 변경과 구분할 수 있도록 프로젝트 관행에 따라 별도 Commit이나 PR로 나눕니다.

## 프로젝트 규칙과 코드 스타일

구현은 자신의 선호보다 기존 구조와 프로젝트의 규칙을 따릅니다. 비슷한 동작을 처리하는 기존 코드와 테스트를 참고하고, 새로운 패턴을 도입해야 한다면 그 이유를 설명합니다.

포맷, 린트, 생성 코드 갱신 방법은 프로젝트의 `CONTRIBUTING`과 개발 문서를 따릅니다.

## 범위 확대의 감지

구현하다 다음 상황을 만나면 일단 멈추고 범위를 다시 평가합니다.

- 예상하지 못한 공개 API와 호환성을 바꾸어야 함
- 하나의 모듈로 예상했던 변경이 여러 서비스와 저장소로 확대됨
- 성공 기준을 바꾸지 않고는 구현할 수 없음
- 새로운 정책·사용자 경험·성능 타협을 프로젝트가 결정해야 함
- 작업 중 발견한 다른 문제를 함께 해결해야만 할 것 같음

범위 확대를 구현 능력으로 버티지 않습니다. 작업이 예상보다 커졌다는 것은 프로젝트와 다시 의견을 맞춰야 한다는 신호입니다.

## 변경 방향의 재합의

범위가 달라졌다면 Issue나 공식 논의 경로에 다음을 남깁니다.

1. 처음에 예상한 범위
2. 구현 중 발견한 추가 조건
3. 예상되는 추가 변경과 영향
4. 작업 분리·중단·확대 중 판단이 필요한 사항

응답을 기다리는 동안 확대된 범위를 임의로 완성하지 않습니다. 답변이 없다면 기존 성공 기준으로 끝낼 수 있는지 다시 판단하고, 불가능하면 작업을 보류합니다.

## 변경 범위 기록

```text
해결할 문제:
포함할 변경:
추가·수정할 테스트:
유지할 기존 동작:
포함하지 않을 변경:
재논의가 필요한 조건:
```
