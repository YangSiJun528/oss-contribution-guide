# 9장. 문제와 완료 조건의 확정

작업을 골랐다면 바로 코드를 고치지 말고 변경 전 상태에서 문제를 재현합니다. 현재 동작, 기대 동작과 성공 기준을 확정해야 변경 후에 문제가 해결되었는지 판단할 수 있습니다.

## 기준 버전과 기준 상태

어떤 Commit·버전·운영체제·실행 환경에서 확인하는지 기록합니다. 가능하면 프로젝트가 안내한 기본 환경에서 변경 전 빌드와 테스트를 실행합니다.

변경 전 상태를 확인하면 원래 있던 실패와 자신의 변경으로 생긴 실패를 구분할 수 있습니다. 초기 테스트가 실패한다면 무조건 고치려고 하지 말고, 현재 작업과 관련된 실패인지 먼저 구분합니다.

## 문제 재현

제쏔 사용자가 문제를 겪는 순서를 직접 따라가고, 가능한 경우 작은 재현 사례를 만듭니다. 재현 사례에는 필요한 입력, 실행 순서, 실제 결과가 포함되어야 합니다.

재현하지 못했다면 원인을 추측해 구현하지 않습니다. 환경 차이, 버전, 누락된 조건을 더 확인하거나 Issue에서 재현 정보를 요청합니다.

## 현재 동작과 기대 동작

문제를 정의할 때는 설명과 판단을 구분합니다.

| 구분 | 기록 내용 |
| --- | --- |
| 조건 | 문제가 나타나는 버전, 환경, 입력과 상태 |
| 현재 동작 | 변경 전에 실제로 관찰한 결과 |
| 기대 동작 | 문서, 스펙, 기존 논의로 확인한 올바른 결과 |
| 차이 | 현재와 기대 동작 사이의 검증 가능한 차이 |

단순히 “잘 동작해야 한다”고 쓰지 않고 테스트나 관찰으로 구분할 수 있는 상태로 적습니다.

## 관련 코드·테스트·변경 이력

재현 경로에서 시작해 관련 코드와 테스트를 찾습니다. 같은 동작을 다룬 과거 Commit, Issue, PR이 있다면 현재 구조를 선택한 이유와 이전에 거절된 대안을 확인합니다.

이 조사의 목표는 코드베이스 전체를 이해하는 것이 아니라 현재 문제의 입력부터 결과까지 연결된 범위를 파악하는 것입니다.

## 문제 원인과 영향 범위

관찰한 증상과 직접적인 원인을 구분합니다. 원인을 완전히 입증하지 못했다면 확정적으로 쓰지 않고, 현재까지 확인한 사실과 가설을 구분합니다.

같은 원인이 다른 경로와 사용자에게도 영향을 주는지 살펴봅니다. 영향 범위를 확인해야 수정할 코드와 필요한 테스트 범위를 정할 수 있습니다.

## 성공 기준

성공 기준은 변경 후 다음을 판단하는 조건입니다.

- 재현 절차에서 기대 동작이 나타나는가?
- 문제를 방지하는 테스트가 있는가?
- 관련된 기존 동작이 유지되는가?
- 프로젝트가 요구한 빌드·테스트·품질 기준을 통과하는가?

이 기준을 정할 수 없다면 구현을 시작하지 말고 Issue의 요구사항을 다시 확인합니다.

## 문제 정의 기록

구현 전에 다음 결과를 남깁니다.

```text
기준 버전과 환경:
재현 절차:
현재 동작:
기대 동작:
확인한 원인:
영향 범위:
성공 기준:
확인하지 못한 내용:
```

> **모임 체크포인트**
>
> 구현 전에 재현 결과와 성공 기준을 공유합니다. 재현하지 못했다면 추측한 원인을 구현하지 않습니다.
