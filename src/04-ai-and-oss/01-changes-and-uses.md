# AI가 바꾼 OSS 기여

AI는 코드를 작성하고 문제를 찾는 데 드는 비용을 크게 낮췄습니다. 이전에는 시도하기 어려웠던 작업을 가능하게 만들었지만, 이해하거나 검증하지 않은 결과까지 쉽게 제출할 수 있게 했습니다. OSS 프로젝트는 두 변화를 동시에 겪고 있습니다.

## 만드는 비용과 검토하는 비용

AI를 사용하면 코드뿐 아니라 Issue, PR 설명과 리뷰 답변도 빠르게 만들 수 있습니다. 그러나 메인테이너는 제출물이 실제 문제를 해결하는지, 기존 설계를 해치지 않는지, 테스트와 설명이 사실인지 여전히 확인해야 합니다. 제출량이 늘어도 메인테이너의 시간은 함께 늘어나지 않습니다.

이 때문에 문제가 되는 것은 AI를 사용했다는 사실 자체보다 **검증 비용을 다른 사람에게 넘기는 방식**입니다. 다음과 같은 제출은 겉보기에는 자세하더라도 프로젝트에 도움이 되기 어렵습니다.

- 직접 재현하지 않은 버그와 실제 동작을 확인하지 않은 취약점 보고
- 프로젝트의 문제와 관계없는 Issue 또는 필요성이 합의되지 않은 PR
- 실행하지 않은 테스트 결과와 존재하지 않는 API에 관한 설명
- 생성된 내용을 이해하지 못한 채 이어 가는 리뷰 답변
- 배지, 현상금이나 기여 횟수만을 목적으로 대량 생성한 제출

이런 저품질 결과를 흔히 **AI slop**이라고 부릅니다. 표현의 기준은 사람마다 다르지만, 여기서는 AI를 쓴 모든 결과가 아니라 제출자가 이해와 검증을 하지 않아 처리 비용을 메인테이너에게 넘긴 결과를 뜻합니다.

## 같은 기술이 만든 상반된 결과

보안 보고는 이 차이를 잘 보여 줍니다. Spring 팀은 AI를 활용한 보안 보고가 크게 늘었고, 그중에는 실제 취약점뿐 아니라 중복되거나 유효하지 않은 결과도 많았다고 설명합니다. 보고 하나마다 전문가가 영향 범위를 확인하고 제보자와 수정 내용을 검증해야 하므로, 그럴듯한 가능성만 제출하는 것으로는 충분하지 않습니다. 반면 Mozilla는 AI 코드 분석으로 찾은 취약점 271개를 Firefox 150에서 수정했습니다. AI가 문제를 찾았다는 사실보다 사람이 재현하고 분류하고 수정할 수 있는 과정이 있었는지가 결과를 갈랐습니다. 자세한 내용은 [Spring의 AI 시대 보안 보고 회고][spring-ai-security]와 [Mozilla의 보안 연구 사례][mozilla-ai-security]에서 볼 수 있습니다.

curl의 경험도 단순한 성공이나 실패로 정리하기 어렵습니다. 저품질 보안 보고가 급증하자 curl은 2026년 2월 버그 바운티를 중단했습니다. 이후 접수 방식을 바꾸어 3월에 다시 열었고, 보고량이 더 늘었는데도 유효한 취약점의 비율은 과거 수준을 회복했습니다. 도구만 막거나 허용하는 것보다 제출 경로, 검증 기준과 참여자의 태도가 함께 영향을 준 사례입니다. 자세한 경과는 curl 메인테이너의 글 [High-Quality Chaos][curl-high-quality-chaos]에서 확인할 수 있습니다.

## 도움이 되는 활용의 공통점

AI가 유용하게 쓰인 사례에는 대체로 다음 요소가 있습니다.

- 해결하려는 실제 문제가 먼저 존재합니다.
- 사람이 목표, 설계와 허용할 위험을 결정합니다.
- 원본 코드, 명세나 기존 동작처럼 비교할 기준이 있습니다.
- 컴파일러, 테스트, 재현 절차와 실제 사용으로 결과를 검증합니다.
- AI가 만든 분량이 아니라 유지할 수 있는 결과를 성과로 봅니다.

Bun의 Zig 코드를 Rust로 옮긴 작업은 큰 규모의 예입니다. 기존 테스트를 공통 기준으로 삼고, 변환 규칙을 먼저 만든 뒤 구현·반대 관점의 검토·수정을 반복했습니다. 100만 줄이 넘는 결과가 생겼다는 점보다 기존 동작을 비교할 테스트와 검증 과정을 먼저 설계했다는 점이 중요합니다. 그럼에도 병합 후 기존에 되던 동작이 깨지는 문제 19개가 발견되어 수정되었습니다. 강한 검증 과정도 위험을 없애지는 못한다는 점까지 함께 봐야 합니다. 작업 과정과 한계는 [Bun의 Rust 재작성 기록][bun-rust-rewrite]과 [실제 PR](https://github.com/oven-sh/bun/pull/30412)에서 볼 수 있습니다.

HwpLibSharp는 Java로 작성된 `hwplib`을 C#으로 포팅하고 이후 변경을 동기화하는 데 AI를 활용한 사례입니다. 반복적인 문법 변환과 원본 변경 추적은 AI에 맡기되, 도메인 지식이 필요한 검증과 두 프로젝트의 관계, 장기적인 방향은 사람이 결정했습니다. 자세한 내용은 [HwpLibSharp 포팅 경험][hwplibsharp-ai-porting]을 참고합니다.

두 사례를 모든 기여에 그대로 적용할 수는 없습니다. 프로젝트 안에서 책임을 맡은 사람이 수행한 대규모 작업과 처음 참여하는 외부 기여자의 PR은 신뢰와 검토 여건이 다릅니다. 좋은 활용 사례가 있다는 이유로 대상 프로젝트의 AI 정책을 건너뛸 수는 없습니다.

## 제출하기 전에 판단하기

AI를 사용했다면 최소한 다음 질문에는 직접 답할 수 있어야 합니다.

- 이 변경이 해결하는 실제 문제는 무엇인가?
- 생성된 코드와 설명을 모두 이해하고 있는가?
- 어떤 방법으로 동작을 확인했고 그 결과를 다시 재현할 수 있는가?
- 잘못되었을 때 직접 수정하고 리뷰에 응답할 수 있는가?
- 프로젝트가 이 사용 방식과 제출 방식을 허용하는가?

공동체의 규칙과 상황을 고려하지 않은 제출의 문제는 [공동체를 무시하는 기여](../03-contributor-attitude/02-ignoring-the-community.md)를 참고합니다.
