# 프로젝트와 작업 정하기

프로젝트를 찾고 기여 가능성을 확인하는 일반적인 방법은 다음 자료에 잘 정리되어 있습니다. 먼저 읽어보기를 권합니다.

- [GitHub에서 OSS에 기여할 방법 찾기][github-find-contributions]: GitHub에서 관련 프로젝트와 작업을 찾는 기능을 설명합니다.
- [AI를 활용한 OSS 기여 가이드와 프롬프트][ai-open-source-contribution-guide]: AI로 프로젝트와 Issue 후보를 조사하는 사례입니다.
- [오픈소스에 기여하는 방법][open-source-guide]: 프로젝트 선택, 활동 상태 확인, Issue·PR에서 소통하는 방법을 다룹니다.
- 공개 자료는 아니지만 TODO: 이름뭐더라 암튼 그 책도 괜찮음.

이 글에서는 위 자료나 앞 장과 겹치는 설명 대신, 이 모임에서 프로젝트와 첫 작업을 고를 때 특히 확인할 내용을 정리합니다.

## 프로젝트 후보 정하기

OSS 기여에는 시간과 노력이 들지만 보상은 보장되지 않습니다. 따라서 자신이 계속 살펴볼 이유가 있는 프로젝트부터 찾습니다.

1. 현재 사용하고 있는 프로젝트
2. 관심 있거나 공부하고 싶은 분야의 프로젝트
3. 사용해보고 싶었던 프로젝트
4. 이전 프로젝트·포트폴리오·지원 분야와 관련된 프로젝트

처음부터 하나로 정하지 말고 후보를 5개 안팎으로 고릅니다.

한 프로젝트에 마땅한 작업이 없거나 기여 정책이 맞지 않아도 다른 후보를 확인할 수 있기 때문입니다.

이 기준으로도 살펴보고 싶은 프로젝트가 없다면 억지로 기여할 필요는 없습니다.
자신이 이해하고 설명할 동기 없이 임의의 프로젝트에서 작업을 지속하기는 어렵습니다.

## 프로젝트의 기여 방법 확인하기

프로젝트마다 사용하는 서비스와 절차가 다릅니다.

저장소의 `README`와 `CONTRIBUTING`뿐 아니라 연결된 공식 웹사이트와 조직 공통 문서도 확인합니다.

일반적으로 README를 보면 어느 경로로 가야 확인할 수 있는지 알 수 있습니다.

이 가이드는 일반적인 상황을 설명합니다. 앞으로 설명할 내용에서 프로젝트가 정한 방법이 있다면 이를 우선하세요.

확인할 문서와 위치는 [프로젝트의 방식과 문화](../02-oss-overview/04-project-culture.md)와 [저장소에서 확인할 파일](../06-appendix/05-repository-files.md)에 정리했습니다. AI를 사용한다면 [프로젝트마다 다른 AI 사용 규칙](../03-contributor-attitude/03-project-ai-policies.md)도 먼저 확인합니다.

## 문서와 실제 운영 비교하기

개인적인 경험으로는 기여 문서가 오래되었거나 실제 운영과 맞지 않는 경우가 종종 있었습니다. 후보를 정하기 전에 최근 Issue와 PR을 직접 확인합니다.

- 새로운 외부 기여자의 PR도 최근에 병합되는가?
- 질문과 PR에 리뷰가 달리며, 거절이나 중단 이유를 설명하는가?
- 문서에 없는 Issue 선행, 테스트, 커밋 규칙이 있는가?
- 진행 중인 PR과 작업하려는 사람이 지나치게 많지는 않은가?

후보를 비교한 뒤 우선순위가 높은 프로젝트 1~2개를 직접 설치하고 사용해봅니다.
적합한 프로젝트가 없다면 후보 찾기부터 반복합니다.

### 몇가지 TIP

GitHub Star 수만으로 기여 난이도를 판단하기는 어렵습니다.
생태계의 크기에 따라서 다르고, 좀 관심이 쏠린 경우면 더 크거나, 지속적인 필요가 있지만, 흔히 재미가 없는 프로젝트의 경우 스타가 적은 편임.

유명 언어·프레임워크의 핵심 저장소나 큰 단체의 대표 프로젝트는 작업 경쟁과 검토 기준이 높을 수 있습니다.
이 경우 같은 생태계의 구체적인 라이브러리나 도구도 살펴봅니다.

커밋이 활발하고(개수나 간격보다는 막 몇달 이상 방치되다가 가끔 처리하고 이런거 말고 간격이 있더라도 꾸준한가?), 외부 기여를 꾸준히 받고, 메인테이너가 빠르게 응답하는 프로젝트가 상대적으로 더 좋습니다.

## 기여할 작업 찾기

첫 기여에서는 기존 Issue 중 범위가 명확한 작업을 찾는 편이 수월합니다.

다음 조건을 확인해보면 좋습니다.

- 현재 동작과 기대 동작이 명확한가?
- 예상 변경 범위와 검증 방법을 파악할 수 있는가?
- 중복 Issue, 진행 중인 PR, 담당자나 선행 작업이 없는가?
  - github assigned 나 코멘트, 연결된 PR을 확인해주세요.
- Maintainer가 문제와 해결 방향에 동의했는가?
- 현재 버전에서도 문제가 재현되는가?

### 몇가지 TIP

오래된 Issue는 아직 유효한지 확인한 뒤 시작합니다. 방치되어 이미 해결되거나 더 이상 작업이 필요없는 상태일 수 있어요.

설명이 부족한 Issue는 쉬워 보여도 원래 의도를 파악하는 데 더 많은 시간이 들 수 있습니다.
해결 조건이 명확하거나 제시된 이슈가 더 나아요.

댓글이 많거나 논의가 불확실하게 끝난 경우는 아직 확실하게 의견이 정해지지 않은 문제일 확률이 높으므로 피하는게 좋습니다.

기여하려는 사람이 많았는데 오래 방치된 경우는 난이도가 높은 작업일 수도 있습니다.

`good first issue`류 라벨이 잘 관리되고 있는지 확인해보세요.
라벨을 관리하지 않는 프로젝트도 있고, 라벨이 있어도 오래되었거나 이미 작업 중일 수 있습니다.
라벨의 개수보다 신규 기여자가 최근에 실제로 리뷰받고 기여를 완료했는지를 확인해보세요.

### 이슈

기존 Issue만 해결해야 하는 것은 아닙니다. 직접 사용하면서 발견한 버그나 불편을 제보하고 해결할 수도 있습니다.

변경 이유를 설명하기에는 이쪽이 더 자연스럽지만, 첫 기여 전에 명확한 문제를 발견하기는 쉽지 않으므로 기존 Issue부터 살펴보는 방식을 앞에 두었습니다.

누군가 작업 의사를 밝혔더라도 참여 가능 여부는 프로젝트마다 다릅니다.

최근 사례로 관습을 확인하고, 불분명하면 Maintainer와 기존 작업자에게 묻습니다. 새 기능, 공개 API 변경, 대규모 리팩터링처럼 영향이 큰 작업도 구현 전에 방향을 합의합니다.

보안 취약점일 가능성이 있다면 공개 Issue 대신 `SECURITY`에 적힌 비공개 신고 절차를 따릅니다.

## 첫 작업 선택하기

첫 작업은 코드가 짧은 것보다 문제와 완료 조건이 명확한 것이 좋습니다.

- 문제와 변경 이유를 자신의 말로 설명할 수 있는가?
- 직접 재현하거나 현재 동작을 확인했는가?
- 자신의 기술 수준으로 변경 범위를 감당할 수 있는가?
- 수정 전후를 비교할 테스트나 검증 방법이 있는가?
- 진행 중인 작업과 충돌하지 않고 프로젝트 정책에 맞는가?
- 이 모임의 목표에 맞는 코드 변경을 포함하는가?

요구가 모호한 대형 기능이나 근거 없는 전면 리팩터링은 첫 작업으로 피합니다.

## 모임에 선택 결과 공유하기

> 이 절은 모임 참가자에게만 적용됩니다.

다음 내용을 Discord에 공유합니다.

- 프로젝트 후보 약 5개와 선택한 이유
- 우선 확인할 프로젝트 1~2개와 기여 가능성을 판단한 근거
- 작업 후보 1~3개의 링크, 예상 범위, 확인이 필요한 내용

하나로 결정하지 못했다면 1순위와 예비 후보를 함께 공유합니다. 유명세나 라벨보다 직접 사용한 경험, 최근 운영 근거, 자신이 이해하고 검증할 수 있는 범위를 기준으로 선택합니다.
