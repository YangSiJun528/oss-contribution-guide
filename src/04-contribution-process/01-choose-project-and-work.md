# 프로젝트와 첫 작업 선택

> **공개 가이드 요약**
>
> [오픈소스에 기여하는 방법][open-source-guide]은 사용하거나 관심 있는 프로젝트부터 찾고, 최근 Commit·Issue·PR을 통해 활동 상태와 기여 환경을 확인하도록 안내합니다. [GitHub에서 OSS에 기여할 방법 찾기][github-find-contributions]는 GitHub에서 후보와 입문자용 Issue를 탐색하는 기능을 설명합니다.

> **이 가이드의 판단**
>
> 아래 내용은 첫 코드 기여를 돕는 모임을 운영하기 위해 정한 기준과 작성자의 경험에 따른 권고입니다. 모든 프로젝트에 그대로 적용되는 규칙은 아닙니다.

## 프로젝트 후보 찾기

기여 동기에 정답은 없지만, 변경을 끝까지 이해하고 설명하려면 자신이 계속 살펴볼 이유가 있는 프로젝트가 좋습니다. 후보는 다음 순서로 찾아볼 수 있습니다.

1. 현재 사용하고 있는 프로젝트
2. 관심 있거나 공부하고 싶은 분야의 프로젝트
3. 사용해보고 싶었던 프로젝트
4. 이전 프로젝트·포트폴리오·지원 분야와 관련된 프로젝트

이 모임에서는 처음부터 하나를 확정하지 않고 후보를 5개 안팎으로 고르기를 권합니다. 마땅한 작업이 없거나 기여 정책이 맞지 않을 때 다른 후보를 확인할 수 있기 때문입니다.

이 기준으로도 살펴보고 싶은 프로젝트가 없다면 기여를 억지로 진행하지 않는 편이 낫습니다. 임의로 고른 프로젝트에서 작업의 의미를 이해하고 동기를 유지하기는 어렵습니다.

## 실제 기여 가능성 확인

프로젝트의 공식 기여 방법이 이 가이드보다 우선합니다. 사용하는 서비스와 문서 위치는 [프로젝트의 구성과 운영 방식](../02-oss-overview/03-people-and-organizations.md)과 [저장소에서 확인할 파일](../02-oss-overview/04-repository-files.md)을 참고합니다. AI를 사용한다면 [프로젝트별 AI 사용 규칙](../03-contributor-attitude/03-project-ai-policies.md)도 확인합니다.

경험상 기여 문서가 오래되었거나 실제 운영과 맞지 않는 경우가 있었습니다. 따라서 문서와 함께 최근 Issue와 PR에서 다음 내용을 확인하기를 권합니다.

- 새로운 외부 기여자의 PR도 최근에 병합되는가?
- Maintainer가 Issue와 PR에 응답하고 거절이나 중단 이유를 설명하는가?
- 문서에 없는 Issue 선행, 테스트, 커밋 규칙이 있는가?
- 진행 중인 PR과 같은 작업을 하려는 사람이 지나치게 많지는 않은가?

GitHub Star 수만으로 기여 난이도를 판단하기는 어렵습니다. 생태계의 규모와 대중의 관심에 따라 숫자의 의미가 달라지고, Star가 리뷰 여력이나 외부 기여 수용 여부를 보여주지도 않기 때문입니다. 유명 언어·프레임워크의 핵심 저장소나 큰 단체의 대표 프로젝트는 작업 경쟁과 검토 기준이 높을 수 있으므로, 같은 생태계의 구체적인 라이브러리나 도구도 함께 살펴봅니다.

Commit 개수나 간격에도 절대적인 기준은 없습니다. 안정된 프로젝트는 변경이 적을 수 있습니다. 단순한 횟수보다 유지보수가 장기간 중단되지 않는지, 필요한 Issue와 PR에 꾸준히 응답하는지를 봅니다.

후보를 비교한 뒤 우선순위가 높은 프로젝트 1~2개를 직접 설치하고 사용해봅니다. 적합한 프로젝트가 없다면 후보 찾기부터 반복합니다.

## 첫 작업 선택

`good first issue` 같은 라벨은 탐색 수단이지 쉬운 작업이나 수용 가능한 작업을 보장하지는 않습니다. 라벨을 관리하지 않는 프로젝트도 있고, 라벨이 붙은 Issue가 오래되었거나 이미 진행 중일 수도 있습니다.

첫 작업은 다음 내용을 확인할 수 있는 Issue에서 고르기를 권합니다.

- 현재 버전에서도 유효한 문제인가?
- 현재 동작과 기대 동작이 분명한가?
- 완료 조건과 예상 변경 범위를 파악할 수 있는가?
- 담당자, 작업 의사를 밝힌 사람, 연결된 PR이나 선행 작업이 없는가?
- Maintainer가 문제와 해결 방향에 동의했는가?

오래 방치된 Issue, 논의가 결론 없이 길어진 Issue, 여러 사람이 시도했지만 완료하지 못한 Issue는 예상보다 어렵거나 방향이 정해지지 않은 작업일 수 있습니다. 작업 전에 최근 상태와 불확실한 요구를 확인합니다.

기존 Issue만 해결해야 하는 것은 아닙니다. 직접 사용하며 발견한 버그나 불편을 해결하면 변경 이유를 설명하기 더 자연스럽습니다. 다만 첫 기여 전에 명확한 문제를 발견하기는 쉽지 않으므로, 이 가이드에서는 범위가 정리된 기존 Issue를 먼저 살펴보기를 권합니다.

누군가 작업 의사를 밝혔더라도 참여 가능 여부는 프로젝트마다 다릅니다. 최근 사례로 관습을 확인하고, 분명하지 않다면 Maintainer와 기존 작업자에게 묻습니다. 새 기능, 공개 API 변경, 대규모 리팩터링처럼 영향이 큰 작업도 구현 전에 방향을 합의합니다.

보안 취약점일 가능성이 있다면 공개 Issue를 만들지 말고 `SECURITY`에 적힌 비공개 신고 절차를 따릅니다.

> **모임 규칙**
>
> 다음 내용을 Discord에 공유합니다.
>
> - 프로젝트 후보 약 5개와 선택한 이유
> - 우선 후보 1~2개와 최근 운영을 확인한 근거
> - 작업 후보 1~3개와 예상 범위, 확인하지 못한 내용
>
> 하나로 결정하지 못했다면 1순위와 예비 후보를 함께 공유합니다.

AI로 후보를 조사하는 구체적인 사례와 프롬프트는 [AI를 활용한 OSS 기여 가이드와 프롬프트][ai-open-source-contribution-guide]에서 볼 수 있습니다.
