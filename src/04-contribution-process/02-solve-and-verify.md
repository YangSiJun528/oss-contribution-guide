# 문제를 재현하고 필요한 변경만 구현·검증한다

> **공개 가이드 요약**
>
> [오픈소스에 기여하는 방법][open-source-guide]은 변경 전에 프로젝트의 기여 문서와 기존 논의를 확인하고, 프로젝트 스타일에 맞춰 필요한 테스트를 수행하도록 안내합니다. 실제 명령과 통과 기준은 해당 프로젝트의 기여 문서를 따릅니다.

작업을 골랐다면 바로 코드를 수정하기보다 문제와 완료 기준을 먼저 확정해야 합니다. 그 범위 안에서 필요한 변경만 구현하고, 제출할 모든 내용을 직접 검증해야 Maintainer가 변경을 검토할 수 있습니다.

## 수정 전에 문제와 완료 기준을 확정한다

- 변경 전 상태에서 빌드와 테스트를 실행합니다.
- 현재 동작과 기대 동작을 정리합니다.
- 관련 코드, 테스트, 과거 Commit·Issue·PR을 확인합니다.
- 문제의 원인과 영향 범위를 파악합니다.
- 무엇으로 성공을 확인할지 정합니다.

변경 전 상태를 확인하면 원래 있던 실패와 자신의 변경으로 생긴 실패를 구분할 수 있습니다. 완료 기준을 먼저 정하면 작업하면서 범위가 불필요하게 커지는 것도 막을 수 있습니다.

## 합의한 문제를 해결하는 데 필요한 변경만 한다

- 문제 해결에 필요한 코드만 수정합니다.
- 관련 없는 리팩터링과 포매팅을 제외합니다.
- 기존 코드 스타일과 프로젝트 규칙을 따릅니다.
- 작업 범위가 예상보다 커지면 계속 구현하기 전에 다시 의견을 묻습니다.

좋아 보이는 개선을 한 PR에 함께 넣으면 변경 이유와 영향 범위를 판단하기 어려워집니다. 별도의 문제라면 별도의 제안이나 작업으로 분리합니다.

## 제출할 변경 전체를 직접 책임질 수 있어야 한다

- 필요한 테스트를 추가하고 포맷·린트·테스트를 실행합니다.
- 전체 diff를 처음부터 끝까지 직접 읽습니다.
- 문제와 무관한 변경을 제거합니다.
- 비밀정보, 개인정보, 로컬 경로가 포함되지 않았는지 확인합니다.
- 디버그 코드, 임시 주석, 불필요한 생성 파일과 lockfile 변경을 제거합니다.
- 실행하지 않은 테스트를 실행했다고 적지 않습니다.
- 자신이 의도하고 이해한 내용만 Commit과 PR에 적습니다.

AI가 변경을 만들었더라도 책임은 제출자에게 있습니다. 코드가 어떻게 동작하는지, 왜 필요한지, 어떤 방법으로 검증했는지를 직접 설명할 수 있어야 합니다.
