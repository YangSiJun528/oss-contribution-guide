# 14장. PR 결과의 수용

PR을 제출한 뒤에는 수정 요청, 병합, 거절, 다른 변경을 통한 해결, 장기 무응답이 모두 가능합니다. 이 결과들은 제출자의 능력에 대한 단일한 평가가 아니며, 프로젝트의 방향과 운영 여력을 포함한 여러 판단의 결과입니다.

## 검토 대기의 원칙

프로젝트마다 검토 속도가 다르므로 모든 PR에 적용할 대기 기간을 정할 수는 없습니다. 자신의 PR만 보지 말고 같은 저장소의 다른 PR과 리뷰가 어떤 속도로 진행되는지 살펴봅니다.

전체적으로 리뷰가 밀려 있다면 유지보수자가 다른 일을 처리하고 있을 가능성을 고려합니다. 기다리는 동안 다른 작업을 탐색하거나 프로젝트를 더 사용해 볼 수 있습니다.

## 공개 경로의 상태 확인

충분히 기다렸는데도 진행 상태를 알 수 없다면 PR의 공개된 대화에서 간결하게 묻습니다. 새로운 정보가 있다면 함께 적고, 단순한 재촉이라면 한 번으로 제한합니다.

반복해 멘션하거나, Issue·PR·Discord·이메일 등 여러 채널에 같은 요청을 동시에 보내지 않습니다. 반복 요청은 리뷰 우선순위를 높여 주기보다 다른 참여자의 응답 비용을 늘릴 수 있습니다.

## 제출 결과의 유형

### 수정 요청

요청을 해석하고, 필요하면 질문하고, 수정 후 다시 검증합니다. 수정했다는 사실만 알리지 말고 [13장의 순서](13-review-dialogue.md)에 따라 변경과 재검증 결과를 남깁니다.

### 병합

병합은 프로젝트가 현재 변경을 받아들였다는 뜻입니다. 후속 수정, 문서 갱신, 릴리스 확인을 요청받는다면 가능한 범위에서 대응합니다. 병합되었다고 해서 즉시 정식 릴리스에 포함되는 것은 아닙니다.

### 다른 변경을 통한 해결

현재 PR이 아닌 다른 PR, 설계 변경, 의존성 갱신으로 문제가 해결될 수 있습니다. 이 경우 자신의 PR이 병합되지 않더라도 문제 해결에 필요한 정보를 제공했을 수 있습니다. 중복된 변경을 유지하지 말고 프로젝트의 안내에 따라 PR을 정리합니다.

### 거절

프로젝트 방향, 유지 비용, 대안, 우선순위 때문에 변경이 거절될 수 있습니다. 거절 이유가 분명하지 않고 추가 학습에 실질적으로 필요하다면 한 번 질문할 수 있습니다. 그러나 판단을 계속 번복시키려고 하거나 개인적 공격으로 받아들이지 않습니다.

### 장기 무응답

충분히 기다리고 공개 경로에서 한 번 상태를 물었는데도 답이 없을 수 있습니다. 제출자가 끊임없이 기다려야 할 의무는 없습니다. 자신의 기록에 상태를 남기고 다른 작업으로 이동하거나 참여를 중단할 수 있습니다.

## PR 제출, 병합과 릴리스의 구분

세 상태는 서로 다릅니다.

| 상태 | 의미 |
| --- | --- |
| PR 제출 | 유지보수자가 변경을 판단할 자료를 공개함 |
| PR 병합 | 변경이 프로젝트의 개발 이력에 포함됨 |
| 릴리스 | 변경이 특정 버전으로 배포되어 사용자에게 전달됨 |

병합된 변경이 어느 버전에 들어가는지는 프로젝트의 릴리스 일정과 판단에 따릅니다.

## 가이드 목표의 평가

변경이 병합되지 않았더라도 다음 조건을 충족했다면 이 가이드의 목표는 달성한 것으로 볼 수 있습니다.

- 유효한 문제와 완료 조건을 확인했다.
- 프로젝트와 필요한 방향을 논의했다.
- 범위를 통제한 변경을 직접 이해하고 검증했다.
- 변경 이유, 검증 결과와 한계를 검토 가능한 형태로 설명했다.
- 리뷰와 프로젝트의 판단에 책임 있게 대응했다.
