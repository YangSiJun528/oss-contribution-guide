# 15장. 기여 경험의 전환

첫 기여의 가치는 PR의 병합 여부로만 결정되지 않습니다. 문제를 재현하고 코드와 이력을 읽고, 변경을 검증하고, 리뷰를 받은 경험은 다음 참여의 기반으로 남길 수 있습니다. 그러려면 결과보다 자신이 수행한 판단과 학습을 기록해야 합니다.

## 최초 목표의 재평가

[1장에서 정한 기여 동기](../01-foundations/01-expectations.md)와 실제 경험을 비교합니다.

- 처음에 기대한 것은 무엇이었는가?
- 실제로 가장 많은 시간을 사용한 부분은 무엇인가?
- 기대하지 못했지만 얻은 것은 무엇인가?
- 다음에도 같은 비용을 감수할 의사가 있는가?

병합되었는지를 성공의 유일한 기준으로 사용하지 않습니다. [14장의 가이드 목표](14-pr-outcomes.md#가이드-목표의-평가)도 함께 평가합니다.

## 획득한 프로젝트 지식

첫 작업을 끝낸 후에는 처음과 다른 지식을 가지게 됩니다.

- 프로젝트의 설치, 빌드와 테스트 흐름
- 특정 영역의 코드와 테스트 구조
- Issue·PR·리뷰의 실제 운영 관행
- 유지보수자가 중요하게 보는 품질 기준
- 문서에서 바로 알기 어려운 프로젝트의 판단 방식

이 지식을 다음 작업에 사용할 수 있도록 구체적인 파일, 명령, 논의와 함께 기록합니다.

## 후속 참여의 선택지

어느 선택이 더 높은 수준의 기여라고 단정할 수는 없습니다. 자신의 동기와 시간, 프로젝트의 필요에 맞는 방식을 선택합니다.

### 동일 프로젝트의 후속 작업

이미 알게 된 코드 영역과 절차를 활용해 비슷한 규모의 문제를 해결합니다. 첫 작업보다 탐색과 환경 구성 비용이 줄어들 수 있습니다.

### 테스트·리뷰·Issue 지원

새로운 변경을 제출하지 않고도 Issue를 재현하거나, 기존 PR을 테스트하거나, 사용자의 질문에 답하거나, 중복 Issue를 정리할 수 있습니다. 이런 활동은 유지보수자의 확인 비용을 줄이고 자신의 프로젝트 지식을 넓힙니다.

### 더 큰 작업의 제안

프로젝트의 방향과 의사결정 방식을 이전보다 잘 이해했다면 더 큰 문제를 논의할 수 있습니다. 큰 작업일수록 코드보다 Issue, RFC, 설계 제안으로 필요성과 방향을 먼저 합의합니다.

### 다른 프로젝트의 탐색

이전 프로젝트와 맞지 않았거나 다른 생태계를 경험하고 싶다면 [6장의 후보 구성](../02-selection/06-project-candidates.md)으로 돌아갑니다. 첫 경험을 보편 규칙처럼 적용하지 말고 새 프로젝트의 문서와 운영을 다시 확인합니다.

### 참여의 중단

더 이상 시간을 쓰고 싶지 않거나 공동체와 맞지 않는다면 잠시 쉬거나 완전히 떠나도 됩니다. 기여를 시작했다는 사실은 계속 참여해야 할 의무를 만들지 않습니다.

## 기여 경험의 기록

경험을 기록할 때는 병합 여부나 변경한 코드 양만 적지 않습니다.

```text
최초 목표:
프로젝트와 작업 선정 이유:
해결하려던 문제:
직접 수행한 분석과 변경:
실행한 검증:
받은 피드백과 결과:
학습한 내용:
다시 한다면 바꿀 점:
다음 참여 선택:
```

이 기록은 다음 작업을 위한 개인 메모로 남길 수도 있고, 다른 사람의 도움이 된다면 공개할 수도 있습니다.

## 외부 공개와 기여 수준

포트폴리오, 이력서, GitHub 프로필과 후기에 경험을 적을 때는 실제 역할을 정확히 구분합니다.

- 직접 발견한 문제인가, 기존 Issue를 해결한 것인가?
- 해결 방향을 제안했는가, 기존 설계를 구현했는가?
- 전체 변경을 작성했는가, 특정 부분만 수정했는가?
- 다른 참여자의 도움과 리뷰를 어떻게 받았는가?
- 변경이 병합되었는가, 다른 방식으로 해결되었는가, 아직 미결인가?

“핵심 개발자”, “메인테이너”처럼 실제로 얻지 않은 역할을 사용하지 않고, 병합되지 않은 제안을 제품에 반영된 성과처럼 설명하지 않습니다. 정확한 역할과 결과를 적는 편이 기여 경험의 가치를 더 명확하게 보여 줍니다.
