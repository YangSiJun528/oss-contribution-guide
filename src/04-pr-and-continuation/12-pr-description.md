# 12장. PR의 설명 구조

PR은 변경된 코드를 보여 주는 곳이자, 검토자가 변경의 필요성·범위·정확성을 판단하는 문서입니다. 검토 가능한 PR은 문제, 해결 방법, 검증 결과와 남은 불확실성을 이 순서로 전달합니다.

프로젝트가 PR 템플릿과 제출 규칙을 제공한다면 그 형식을 우선합니다. 템플릿의 항목을 지우거나 확인하지 않은 내용을 임의로 채우지 않습니다.

## 문제와 변경 필요성

검토자가 코드부터 읽지 않고도 변경해야 할 이유를 알 수 있게 적습니다.

- 어떤 조건에서 문제가 나타나는가?
- 현재 동작과 기대 동작은 무엇인가?
- 사용자나 프로젝트에 어떤 영향을 주는가?
- 어떤 Issue와 논의에서 필요성이 확인되었는가?

Issue에 세부 내용이 있더라도 링크만 남기지 않고, PR을 읽는 사람이 변경 이유를 파악할 정도로 요약합니다.

## 해결 방법과 변경 범위

어떤 방법으로 문제를 해결했는지를 설명합니다. 파일 목록을 나열하기보다 동작이 달라진 방식과 그 선택의 이유를 적습니다.

- 핵심 변경은 무엇인가?
- 이 방법을 선택한 이유는 무엇인가?
- 의도적으로 바꾸지 않은 범위는 무엇인가?
- 구현 중 추가된 판단과 타협이 있는가?

리팩터링, 포맷팅, 의존성 변경이 포함되었다면 문제 해결에 필요한 이유를 특히 명확히 합니다.

## 테스트와 검증 결과

[11장에서 실제로 수행한 검증](../03-change/11-final-verification.md#검증-결과의-표현)만 적습니다. “테스트 통과”로 요약하기보다 명령·환경·결과를 검토자가 판단할 수 있는 형태로 남깁니다.

```text
## 검증

- `실행한 명령`: 통과·실패와 중요한 결과
- 수동 재현 절차: 확인한 동작
```

프로젝트가 테스트 체크리스트나 CI를 제공한다면 그 기준과 함께 적습니다.

## 한계와 미확인 사항

모르는 내용을 숨기면 PR이 더 완성도 높아 보이지만, 검토자는 그 부분을 확인하지 못합니다. 아는 한계와 검증하지 못한 환경을 직접 적습니다.

- 특정 운영체제·버전·하드웨어에서 테스트하지 못함
- 성능과 메모리 영향을 정밀히 측정하지 못함
- 관련 특수 사례의 동작을 확인하지 못함
- 후속 작업으로 남긴 범위가 있음

중요한 한계가 PR의 타당성을 바꾼다면 제출 전에 먼저 논의합니다.

## 관련 Issue

연결된 Issue, 사전 논의, 대체되거나 의존하는 PR을 연결합니다. 프로젝트의 관행에 따라 `Fixes`, `Closes`, `Refs` 등 자동 연결 키워드를 사용합니다.

해당 PR이 병합되는 순간 Issue를 닫으면 안 되는 경우에는 자동 종료 키워드를 사용하지 않습니다.

## Commit 구조와 공개 정보

Commit 메시지와 단위는 변경 의도를 드러내야 합니다. 프로젝트가 정한 형식과 sign-off 조건이 있다면 따릅니다. 문제 해결과 관계없는 실험 Commit, 중간 백업, 무의미한 메시지를 그대로 남기지 않습니다.

Commit에 공개할 의도가 없는 이메일과 제3자의 정보가 포함되지 않았는지도 확인합니다.

## Draft 상태

구현 방향이나 특정 부분에 대한 피드백은 필요하지만 아직 검토 준비가 끝나지 않았다면 Draft PR을 사용할 수 있습니다. Draft라는 표시가 미완성 변경을 설명하지 않아도 된다는 뜻은 아닙니다.

어떤 피드백이 필요한지, 완료된 부분과 미완성 부분이 무엇인지, 어떤 검증을 수행했는지를 함께 적습니다.

## PR 설명 템플릿

프로젝트에 자체 템플릿이 없다면 다음 구조를 사용할 수 있습니다.

```text
## 문제
- 현재 동작과 변경이 필요한 이유

## 변경
- 해결 방법과 변경 범위

## 검증
- 실행한 테스트와 결과

## 한계
- 알려진 한계와 확인하지 못한 내용

## 관련 작업
- Issue와 관련 PR
```
