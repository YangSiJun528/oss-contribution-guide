# 13장. 리뷰 대화의 운영

리뷰 대응은 요청한 코드를 변경하는 일로 끝나지 않습니다. 요청의 의미를 확인하고, 동의 여부를 기술적 근거로 판단하고, 수정한 결과를 다시 검증한 뒤 대화에 남겨야 합니다.

## 리뷰 요청의 해석

리뷰 댓글을 받으면 바로 코드부터 수정하지 않습니다. 요청이 다음 중 무엇인지 구분합니다.

- 필수적인 수정 요청
- 대안에 대한 제안
- 설명과 근거를 요청하는 질문
- 사소한 표현·스타일 지적
- 현재 PR의 범위를 벗어난 후속 제안

요청의 종류를 알아야 수정, 설명, 대안 제시, 후속 작업 분리 중 적절한 답을 선택할 수 있습니다.

## 모호한 요청의 확인

요청을 여러 방식으로 해석할 수 있다면 자신이 이해한 내용을 짧게 다시 적고 확인합니다.

```text
요청하신 내용을 다음과 같이 이해했습니다.
- 변경할 부분:
- 유지할 동작:
- 확인할 테스트:

이 방향이 맞는지 확인 부탁드립니다.
```

질문하는 것보다 잘못 이해한 수정을 완성한 뒤 다시 고치는 것이 더 많은 비용을 만듭니다.

## 동의와 이견의 근거

리뷰 요청에 동의한다면 수정하고 검증합니다. 동의하지 않는다면 “원래 코드가 더 좋다”는 선호로 답하지 않고 다음과 같은 근거를 제시합니다.

- 현재 성공 기준과 요구사항
- 기존 프로젝트의 패턴과 설계 원칙
- 코드와 테스트로 확인한 동작
- 제안된 변경이 만들 수 있는 호환성·성능·유지보수 영향
- 요청의 목적을 만족할 다른 대안

이견을 남긴 뒤에는 프로젝트의 최종 판단을 따릅니다. 판단이 자신의 목표와 맞지 않는다면 변경을 중단할 수도 있습니다.

## 수정과 재검증

리뷰를 반영한 뒤에는 수정한 줄만 보지 않고 전체 diff와 관련 테스트를 다시 확인합니다. 작은 수정도 기존 성공 기준을 깨뜨리거나 새로운 변경을 포함할 수 있습니다.

1. 리뷰 요청을 반영합니다.
2. 성공 기준을 검증하는 테스트를 다시 실행합니다.
3. 전체 diff를 다시 읽습니다.
4. 실행한 검증과 결과를 기록합니다.

## 변경 결과의 설명

수정한 뒤에는 “반영했습니다”라는 답변만 남기지 않습니다. 무엇을 바꾸었고, 어떤 검증을 다시 실행했는지 요약합니다.

```text
요청하신 방향으로 다음을 수정했습니다.
- 변경:
- 유지된 동작:
- 재검증:
```

리뷰어가 다시 코드를 추적하지 않고도 요청이 어떻게 반영되었는지 파악할 수 있게 합니다.

## AI 생성 답변의 검토

AI가 리뷰 댓글을 요약하거나 답변 초안을 작성했더라도 제출자가 원문 댓글과 코드를 다시 확인합니다. 리뷰어의 의도를 잘못 요약하거나, 실행하지 않은 검증을 통과했다고 적거나, 프로젝트의 대화 방식과 맞지 않는 표현을 사용할 수 있기 때문입니다.

제출하는 답변은 자신이 이해하고 동의한 내용만 남깁니다.
